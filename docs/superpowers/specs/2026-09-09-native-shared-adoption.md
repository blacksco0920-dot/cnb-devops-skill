# 原生 Caddy 上追加同一所有者的项目

用户已明确将第二个项目追加到原测试/生产服务器，保留第一个项目；这是原首接验证计划的实际范围调整。目标是让相同条件下的后续项目复用固定入口，不要求用户理解路由或编写脚本。

## 已确认的差异

原生 `configure-native-caddy.py` 和 `setup-project.py` 都只接受无 import 基线，不能直接追加第二个项目。既有共享 Caddy v1 适配的是容器入口与发布时路由事务，不可冒称已覆盖 systemd Caddy。第二项目还有同域 web/API/移动网页需求。

## 选择与边界

采用**同一所有者、原生 Caddy、管理员维护静态路由**的限定路径，保留已有 systemd Caddy 和活动应用控制器。另两种做法——迁移入口到 Docker、把路由写入每次应用发布——都会扩大本次主机改动和维护成本，不采用。

只接纳 Skill 生成且能逐字对照已安装 policy 的显式站点片段；未知片段、任意 import、通配符、环境替换、所有者或运行配置漂移仍拒绝。它是运维共存模式，不承诺 Docker 组用户之间的不可信租户隔离。复杂或不明所有权继续走既有共享契约。

## 固定入口应具备的能力

1. **只读原生盘点。** 核验运行中的原生服务、主配置、完整固定 import 闭包及关联已安装 policy；记录项目、域名、回环端口和摘要。不得调用容器盘点器伪造原生证据。
2. **共用预检。** setup 在账号、数据库等资源创建前调用相同检查；检查现有路由、域名/端口冲突及未解决管理员事务。重复接入按本项目片段识别，不要求本项目 import 永远位于文件末尾。
3. **管理员静态追加。** 保留旧主配置/片段原字节。完整候选 validate 后才写入；同时持有旧 helper 的固定锁和新的持久事务锁，记录写前状态，reload 后回读全部配置。崩溃或不确定写入保留现场，后续管理员操作被阻断，固定恢复入口只接受该事务已知的前后状态。
4. **同域应用入口。** 允许显式 `host.native_caddy_gateway: <service>`。该应用服务负责项目内部路径代理，Caddy 只转发项目域名到其固定回环端口；三个服务仍分别验证真实发布身份。省略该字段保持原来的逐服务域名映射。
5. **接入交接。** 真实共享变更前需已有路由/应用基线、覆盖 Caddy 配置及证书的离机实际恢复、适用的凭据轮换记录和管理员维护范围。已有 PG/uploads 恢复不能冒充整机或入口恢复。只对确有暴露、失效或范围变化的凭据处理轮换，不假设每次追加必然暴露秘密。

管理员变更和普通应用发布分别记录。普通发布继续零 Caddy 写权限，不利用首次安装升级第一个项目的控制器；当前项目安装及共享前置未就绪时，不开始其发布。维护期间应核对并协调已有管理员写入者，新的锁不能作为旧写入者已停止的证据。

## 验证与交付顺序

本地覆盖第二/第三项目追加、旧项目续接、域名和回环端口冲突、未知/被改片段、运行漂移、并发、断电式中断及恢复；失败必须先于应用迁移。两个主机分别进行真实验收：原项目基线与保留验证、新项目部署及业务/恢复、再次更新新项目后原项目仍正常。

先交付测试；生产遵守业务仓库的人为合入与候选审批。文件生成、本地测试、主机 setup ready、测试共存和生产共存是不同状态。此文为已授权目标下的实施设计，不是任何门禁的成功回执。

官方行为依据：[Caddy 命令与 validate/reload](https://caddyserver.com/docs/command-line)、[import](https://caddyserver.com/docs/caddyfile/directives/import)、[数据目录](https://caddyserver.com/docs/conventions#data-directory)。实际兼容性以主机已安装版本的检查为准，不升级公共组件来适配当前文档。
