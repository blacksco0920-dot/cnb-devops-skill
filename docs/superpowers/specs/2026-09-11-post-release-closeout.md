# 固定发布核验与状态收尾

用户已批准下一阶段第 1 项：补齐生产结果回读、参数化共存检查和当前状态更新。验证沿用已完成的真实发布，只执行只读云端/主机检查和本地文件写入；不重新部署、升级活动包或重装主机。

## 问题与结果

目前 `release-session` 停在签名发布，不能识别实际部署已完成；它在状态查询中先检查当前时间的签名有效期，可能把已合法执行的历史发布误导为重新批准。共存核验仍是项目专用脚本，当前状态也存在手工修正旧指针的工作。

完成后，AI 使用三个固定入口取得实际发布回执、核对声明的共享主机基线，再从证据更新项目原有的私密状态及状态文档。历史成功、当前运行观测和业务验收分别记录，不互相代替。

## 范围与接口

1. `release-session.mjs verify --spec … --invocation-id … [--apply]`：默认离线预览；apply 仅执行 CNB GET、TAT Describe 和本地记录。复用标准候选/签名/执行请求/回执验证器，以真实执行起止时间验证当时授权。原生批准、Invoke、现有签名/发布有效期门禁不变。原文和 `cnb-deployment-verification/v1` 回执一次发布到 `session/deployment-verification/`；状态查询验证该证据后可返回历史部署完成，不代表主机此刻仍运行该版本。
2. `verify-coexistence.py --spec … [--apply]`：声明自己的服务与运行约束、需保留的邻居容器/文件、Caddy 基线和公开探针；只读采集并比较。输出 `cnb-coexistence-verification/v1`，区分真实观测和测试 fixture。每次真实采集使用新证据目录，不覆盖前态。无业务项目名、服务数量或主机路径硬编码。
3. `reconcile-project-state.py --spec … [--apply]`：只读绑定的发布、共存、业务/UI、恢复及资源引用，写入现有私密状态的 `environments.<environment>.current` 和原状态文档的受管块。`current` 是该环境的接管入口；旧状态全文保存为私密快照，其他环境、历史、用户授权和未拥有字段保持。有限当前别名同步，不推断任意旧字段含义。缺少声明必需的业务验收时只记录已部署与待办，不能写成全范围验收成功。

## 本地收尾约束

spec 包含项目目录、项目/环境、现有私密状态文件、原状态文档、私密事务目录、发布回执路径/摘要、必需检查名、可用检查回执及可选资源引用。检查名限 business/ui/coexistence/recovery；业务/UI 使用项目自己的验收程序，本次不把业务逻辑移入 Skill。

输入有界读取、拒绝符号链接及不安全权限，验证回执摘要、版本/构建/环境与全部声明检查。文档仅写安全摘要，不复制秘密、原始云响应或私密文件内容。preview 零写；apply 使用锁、原文快照及事务记录；两文件任一写入中断后，同输入可核对续接。相同输入重复执行零重写；输入、状态或未受管正文发生第三方修改则停止，不盲目覆盖。

## 验收

- 过期但当时有效且确实完成的发布可只读核验；未执行/错目标/错候选/错签名/输出截断/失败任务仍阻断。
- 不同项目名和服务数量使用同一共存程序；邻居重启、挂载/配置漂移、错镜像或公开身份错误均被发现。
- 收尾不会把未验收、fixture 或错版本记录当作实际完成；重复及部分写入续接保留历史与授权。
- 已有生产回执及真实只读主机采集通过新入口；没有重新部署、运行业务写入或恢复导出。
- 文档仅补相应路由和精简参数说明；活动 bundle 不变，不借本次宣称首次接入整体提速。
