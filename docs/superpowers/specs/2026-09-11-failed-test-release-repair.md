# 测试发布失败后的安全续接：拟议范围

状态：用户于 2026-09-11 确认实施。设计范围为测试环境失败发布续接；生产与其他项目不纳入控制器升级。

本轮已经证实：完整构建、测试和镜像推送成功；应用迁移、启动和容器健康通过，发布身份的响应封装不匹配使最后验收失败。当前应用可运行，但正式发布记录仍为空库起点，失败事务正确阻止后续发布。不能把这种状态记录为已发布成功。

## 建议方案

1. 保留已迁移数据库、上传目录、失败事务和迁移前快照。先让固定恢复入口支持从“已明确绑定的失败事务”采集数据，在另一台 Docker daemon 上完成真实恢复和逐表、目录对账；失败来源使用独立记录，不伪装成成功版本。
2. 管理员入口核对恢复结果、旧事务和现场，签发一次、短时、限定新提交及完整镜像集合的修复许可。修复镜像仍来自正常完整 CI。增加 API 可触发的测试修复事件，复用同一次构建的镜像和身份，不让用户手动拼参数或再次构建。
3. 固定 TAT 在原发布锁下核验许可和现场，永久保留旧事务，再原子接入新的修复事务；重新备份当前数据，执行已审迁移及原有健康、公开身份检查。全部通过才写成功记录并创建候选；再次失败继续保留现场和阻断。

## 第一版边界

先支持测试环境中迁移完成、运行健康而公开探针失败的场景。修复提交的迁移文件必须与失败版本一致；涉及新的数据库结构变更、迁移中断或未知现场的情况继续转人工恢复审阅。正常发布请求的权限和可执行命令不扩大。

只升级新增项目的测试发布控制器与对应固定 TAT 配置，升级本身也要有摘要核验、持久事务及中断续接。已有项目与生产环境不纳入此项变更。

## 验收

- 失败事务、完整数据和快照始终可追溯；没有无标记的恢复空窗，也没有假成功记录。
- 错误或过期许可、不同提交/镜像、数据或配置漂移、中断后未知状态均被拒绝。
- 真实隔离恢复通过后，用正常构建的同一组镜像完成修复发布与候选核验。
- 再核对原有项目的容器、挂载、路由和公开版本保持原状。

## 取舍

推荐该非破坏续接方案。清空新项目数据库虽可能更快，但不能改善保留业务数据时的复用能力；修改成功记录或直接删失败标记也不能作为恢复。

接口封装的小修复与本提案分开验证；它已按当前已安装探针约定完成本地适配，不需要变更业务接口或主机策略。
