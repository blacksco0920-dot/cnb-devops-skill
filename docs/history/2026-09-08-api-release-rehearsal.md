## 效率口径与问题

从任务开始 `2026-09-08T14:43:49Z` 到最后一份恢复证据形成 `2026-09-08T15:23:43.868Z`，共 **2394.868 秒（39.91 分钟）**。包含发布前准备、云端执行、人工等待、失败诊断和阶段衔接；收尾独立复核及文档整理另计。开始至测试 push 的准备约 5 分 16 秒，也包含在此总数中。

记录的 main 授权、就绪按钮和生产批准等待分别约 428.819、72.566、34.660 秒。main 等待期间完整执行了测试恢复，不能再把这段恢复耗时加到总墙钟上，也不能简单扣除全部等待作为“纯自动耗时”。按钮实际触发至 AI 收到回复的间隔另属衔接时间。

可比较的测试流水线为前轮 645.217 秒 → 本轮 585.931 秒，减少 **59.286 秒（9.19%）**。流水线代码没有变化，单次构建缓存、网络和主机拉取波动没有被控制，不能将全部差值归因于新 API 方案。前轮 28.74 分钟包含实际重装与首装，本轮复用现有主机，人工等待条件也不同，不能据此声称整轮加速或给出新项目时限。Token 用量未采集。

本轮仍有可避免的执行开销：

1. 主机采集的辅助路径选择出错；测试恢复前又有两次辅助读取失败，均发生于导出和暂停源服务之前。成功恢复批次仅 67.969 秒，完整窗口多出 218.548 秒准备、诊断与调度，全部保留在记录中。
2. 本机签署时遗漏生产子包的锁定 SDK 安装，程序在读取私钥前停止；按原文已有的 `npm ci` 命令补齐后签署、发布通过。不是云端权限问题，也没有新增授权或替换发布程序。
3. CNB CLI 的 Tag 详情返回一次 500，改用标准 Git 获取原 annotated Tag，再执行包内候选门禁验证；没有重建候选或改写候选内容。

下一步提效应集中在执行衔接：测试构建运行时提前准备生产依赖和两环境恢复命令；严格使用已有完整入口与已验证配置，避免临时猜测路径或重复检查同一安装状态；保留统一时间记录与故障续接位置。这些是本轮暴露的改进方向，不是已经实现的新自动化能力。本轮只补充验证记录，不改运行包。

## 证据边界

这证明了新 API 入口能衔接既有发布链路的日常复用；不等于新版 `preview.3` 活动运行包、完整新账号初始化、第二个陌生项目或共享主机已经验收。首次项目适配及 Secret 内容保存仍应分别验证。

业务检查使用真实 OCR，字段提取仍为 MockExtractor；不证明真实 MiniMax、完整前端 UI 或租户隔离。恢复覆盖 PostgreSQL 与声明的 uploads，不覆盖 Redis、可重建 OCR 缓存、运行秘密、整机或生产原地回退。原始回执、备份和签名材料保留在受保护任务记录，公开文档不含凭据或本机私密路径。
