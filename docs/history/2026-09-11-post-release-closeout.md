# 发布后固定收尾入口实测

本轮把已经完成的生产发布用于只读验证，重点是减少下一次接管时重新查资料、临时编写脚本和手修状态的工作。日常使用从[发布后收尾](../../references/post-release-closeout.md)进入，不依赖本历史记录或任何业务项目源码。

## 固定能力

- `release-session.mjs verify`：沿用原会话和精确生产 invocation，交叉验证候选、签名、实际 TAT 请求及回执、CNB annotations。签名按实际执行窗口核验；已完成历史发布不因今天过期而要求再次批准，新的签名及发布仍遵守原有效期。
- `verify-coexistence.py`：根据本项目服务、邻居基线、控制文件及探针声明执行只读采集。不同项目、服务数和端口不需要修改执行脚本。
- `reconcile-project-state.py`：从固定回执更新原私密状态及原状态文档的受管块。声明缺失的检查继续列为待办；事务保留前态，两文件写入中断可续接，相同输入重复执行不重写。

业务与页面验收程序仍属于业务仓库。状态收尾只核对已有结果的范围和绑定，不执行项目脚本，也不代替发布授权或实时检查。

## 真实结果

声明式共存采集覆盖 7 个受保护容器、21 个控制文件、3 个应用服务、6 个版本探针及 3 个可用性探针，生成的 98 项检查全部通过。此数由声明产生，不是其他项目必须凑齐的门槛。保留原安装后基线及归一化来源摘要。

已有业务、页面、PostgreSQL 与 uploads 恢复回执通过收尾绑定；本次没有重跑业务写入、恢复导出或生产发布。状态与文档已更新，重复执行的状态、文档、回执字节及修改时间全部不变，其他环境和原用户授权保持。运行观测有独立时间，不代表持续健康。

## 验证与限制

发布相关 135 个行为用例、共存 16 个、收尾 11 个、主机准备 17 个、恢复入口 27 个及包检查 32 个通过；它们验证执行程序及安全边界，不是应用的前后端测试。新增行为先以失败用例复现，再实现通过；独立复查补齐了共存候选/策略摘要绑定和完整发布证据集合要求。模拟中断覆盖状态已写而文档未写的窗口，验证不会重复执行部署或覆盖第三方文档修改。

另以全新上下文子智能体做一次文档接管练习：只给 Skill 路径及“陌生项目昨晚已批准、今日签名过期、共享主机、业务通过但页面回执缺失”的场景，不给旧会话、历史或实现计划。它按路由找到三个固定入口，选择按真实执行窗口只读核验、保留页面待办、不重复批准，并将页面程序留在应用仓库。这是定性的只读决策练习，不是第三项目真实部署或全流程效率测量。

活动 bundle 仍为 `0.2.0-preview.5`，没有修改主机运行程序或云资源。此轮验证固定收尾和接管能力，不是陌生项目首次接入计时；持续负载、跨信任租户隔离、独立新会话完整部署和 CI 效率优化仍属后续工作。
