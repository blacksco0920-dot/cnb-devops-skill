# 镜像缓存与导出成本实测

## 范围

继续在 FinAgentCrm 验证已有流水线的构建效率，应用提交 `fff71108246dc7c86f5f18ef260101f4c512864f`。沿用 `0.2.0-preview.5` 活动部署包，只调整四个项目 Dockerfile；业务、依赖版本、检查范围和生产治理保持原样。

- API：发布身份参数移到依赖安装、编译、生产依赖裁剪及 Prisma 生成之后。
- Web：先安装依赖、编译共享包，再写入版本信息并执行 Next 构建。
- Mobile：精确复制 workspace 清单后安装，再复制源码；H5 构建与身份写入分开。
- 验证镜像：pnpm 下载缓存使用明确 `store-dir` 的 BuildKit 挂载，首次 apt 索引在产生它的层内清理。Chromium、系统库和安装产物继续随镜像交付。

项目的具体 Dockerfile 留在项目仓库；Skill 的 [bootstrap](../../references/bootstrap.md)只增加按需测量、分层、缓存命中/失效及独立运行的判断方法。其他项目无需读取本项目或旧会话。

## 验证镜像的本机结果

使用同一 Docker 29.4.3、Linux ARM64、固定 Node 基础镜像和源码快照，顺序构建旧、新镜像。首次尝试受本机 Docker 无效代理影响，未进入依赖安装；随后仅在两次测量命令中清空代理构建参数，没有修改全局配置。基线 pnpm 下载缓存未挂载，优化使用新的专用缓存标识；没有清理全局缓存。

| 指标 | 基线 | 优化后 |
| --- | --- | --- |
| `docker image inspect .Size` 报告值 | 833,269,734 字节 | 720,441,535 字节（减少 13.54%） |
| history 中依赖安装层快照占用 | 2.32 GB | 2.17 GB |
| history 中首次 apt 层快照占用 | 153 MB | 134 MB |
| 导出与解包 | 97.6 秒 | 80.1 秒 |
| 整次本机构建墙钟 | 264.243 秒 | 267.226 秒 |

本机 containerd 的 inspect 指标采用打包资源口径，history 是解包快照占用且显示值已取整；两者不能相加或当作实际网络流量。实现口径见 [Docker inspect](https://github.com/moby/moby/blob/docker-v29.0.0/daemon/containerd/image_inspect.go#L163) 和 [history](https://github.com/moby/moby/blob/docker-v29.0.0/daemon/containerd/image_history.go#L46)。首次下载、硬链接导入与运行条件仍影响时间，局部导出减少不能代替整体提速证明。

联合 `du` 先统计 node_modules，再统计 store，基线 store 仍额外占用 216,984 KiB；优化镜像已无该下载缓存。由于跨挂载导入方式不同，node_modules 自身占用也有变化，不能简单拿 store 数值当作整张镜像减少量。

优化镜像在**无网络、无宿主依赖或缓存挂载**的新容器中通过 pnpm 启动、Prisma/bcrypt 与 Chromium 运行检查。随后复用已有独立数据库 runner，直接运行已构建镜像中的原 worker，完整通过 check、70 项单元、25 项 Chromium E2E、H5 构建及 12 项 smoke。该次 worker 不重新构建镜像；两类证据分别记录。现有 runner 的 5 项检查及独立 Dockerfile 复审通过。

## 应用缓存与云端结果

本机同一 builder 的 17 次依赖层实验全部符合预期。旧 Mobile 两次仅身份不同的构建都重新安装依赖；新 API/Web/Mobile 的结果一致：

| 输入变化 | 依赖安装层 |
| --- | --- |
| 首次构建 | 执行 |
| 原样重复、仅发布身份、仅普通源码 | 命中缓存 |
| 工作区清单 | 失效并重新执行 |

该矩阵仅构建到安装层，以实际 BuildKit `CACHED` 记录判断，不能将其秒级耗时当作完整镜像构建。随后 7 次完整应用镜像构建全部通过。仅身份变化时，API 的编译、生产依赖裁剪和 Prisma 生成，以及 Mobile 的 H5 编译均命中缓存；Web 复用依赖与共享包，仍重新执行确实消费身份信息的 Next 构建。

本机完整镜像的身份输入是独立测量 fixture，不是本轮云端提交；Web 还加入并移除临时源码标记，以检查缓存不会掩盖源码更新。最终镜像实际运行通过 12 项检查：API 的 HTTP 身份不能被运行环境变量覆盖，Prisma/bcrypt 离线可用；原 Web 启动命令与 Mobile Caddy 提供正确身份及 no-store、页面和 16 次真实引用资源响应；源码标记内容精确一致。Web/Mobile 使用唯一临时 bridge 和本机回环端口，未连接真实数据库；该项不包含真实登录或浏览器 JavaScript 执行。

本机运行检查首次使用 internal 网络时，Docker 未创建请求的公开端口；镜像已启动，但 HTTP 检查尚未执行。仅将测量网络改为独立 bridge 后通过，原失败记录保留；没有因此修改应用镜像。所有本轮临时运行容器、网络已清理。

## 证据与边界

本机原始构建日志、尺寸、离线检查和缓存测量在项目私密 `image-cache-20260911/` 中，由项目既有状态文档索引。总索引 `verification-summary.json` 的 SHA256 为 `46d8b1635a23e792b879a7bb55da54cbb4b37d664e9b212558080ea0b1ea1cd6`，分别绑定测量输入、缓存结果、最终镜像运行与云端证据。测量上下文和缓存失效 fixture 位于私密目录，不进入应用提交或镜像发布流程。

本机 ARM64 数据不能替代云端 AMD64；同一 builder 的缓存命中不能证明不同 CNB 任务会共享缓存。生产发布、在线完整业务/UI、主机资源共存与恢复本轮未重验，前轮证据保留原身份。总 token 用量未可靠采集。
